# ReAct 候选检索与审核

城市漫步、景点游览、餐厅推荐共用 `services/candidate_search.py` 的 `ReActCandidateSearch`。使用当前配置的生成模型与高德工具，在路线查询之前审核候选。主 Agent 意图路由和后续选点仍使用原有 Jev。

## 工具循环

```text
原始类别 + 偏好补充 + 固定城市、起点和半径
    ↓
生成模型调用 search_places(keyword, types)
    ↓
代码调用高德，返回真实 ID、名称、类别、地址和 typecode
    ↓
模型阅读结果，调用 review_candidates(accepted_ids, summary)
    ├─ 全部合格：结束当前类别
    └─ 部分不合格 / 没有合格结果：保留合格结果，要求更精确的关键词重搜一次
                                             ↓
                                      再次审核，结束当前类别
    ↓
只合并审核通过的原始 POI → 代码核实路线与预算 → Jev 选择
```

这是带真实工具调用和工具观察的循环。模型的 `tool_calls` 决定搜索词与审核结果，代码执行工具并以 `ToolMessage` 回传观察。不会把模型生成的地点名或坐标当作高德结果。

例如“陕西菜馆”搜到“陕西酒店管理有限公司”：模型应根据公司类别拒绝该 ID，改为“陕西面馆”等同义但更精确的关键词搜索。关键词可以调整，原始类别不能换成另一种菜系。搜索来源仍记在“陕西菜馆”名下，城市漫步的顺序和末站不会因改词失去关联。

## 范围与上限

- 每类最多两次高德搜索；正常两轮模型调用，有重搜时通常四轮，最多六轮，超出返回错误。
- 每次最多观察 20 个去重且在半径内的 POI。模型只能接受当前批次中的真实 ID。
- 未审核当前批次不能继续搜索，不能重复同一关键词与类别组合。
- 一批中有不合格地点时，保留已接受地点并重搜一次；第二次仍不合格的地点排除，不回退到未审核候选。
- 城市、起点、半径由调用方固定。请求内最多两类同时执行 ReAct，每类包含排队最多 90 秒；高德原有请求内四并发限制保留。
- 城市漫步仍按原始偏好保留检索关联并限制每类候选数。景点、餐厅保留现有的类别代码、距离及后续路线硬过滤。
- 全部高德搜索失败与“成功搜索但没有符合要求的地点”分开处理。检索模型调用失败、超时或超过轮数返回 `502 / 50006`；无合格地点按原来的业务错误处理，失败不保存行程。

审核依据是高德已有字段的语义，不代表核验餐厅“正宗”程度、菜单、过敏原、开放时间或其他未提供事实。模型仍可能误判，具体结果需要结合真实数据检查。

## 代码与验证

- `services/candidate_search.py`：工具参数、当前批次、已接受 ID、搜索次数与 ReAct 循环。
- `dependencies.py`：请求内复用检索组件及生成模型连接。
- `services/walk_routing.py`：城市漫步按原类别汇总审核后的 POI。
- `agents/discovery.py`：景点与餐厅共用入口。
- `tests/test_candidate_search.py`：管理公司排除、部分结果保留、改词重搜、ID 越界、次数、超时、取消及三个规划入口接入。

工具消息机制参考 [LangChain 模型工具调用](https://docs.langchain.com/oss/python/langchain/models#tool-calling) 和 [工具文档](https://docs.langchain.com/oss/python/langchain/tools)。沿用现有 `langchain-core` 和模型适配器，没有新增依赖。
