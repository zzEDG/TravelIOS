# 三个旅行 Agent 流程统一：改动说明

## 本次目标

整理 CityWalk、景点和美食 Agent 的公共规划流程，消除重复搜索、锁定地点合并和响应地点构造代码。保留城市漫步的逐站路线、顺序、步行距离、总时长和锁定地点约束。

三个入口现在遵循相同的总体流程：读取并合并状态 → 准备候选（含锁定状态）→ 按各功能规划 → 构造统一地点结果 → 返回和保存。

## 代码改动

### 1. 共用候选准备与地点构造

文件：`backend/app/agents/discovery.py`

- 新增 `prepare_candidates()`：三个 Agent 通过同一个入口决定是否需要搜索、传入搜索半径及 `state.search_limit`。目标名额全部锁定时都跳过搜索。
- 城市漫步通过该入口把旧计划中的锁定点合并到搜索候选；锁定点仍使用旧计划保存的 POI 信息。
- 新增 `planned_place()`，三个 Agent 共用地点 ID、坐标、来源、来源链接及检索时间的结果构造。
- 景点、美食原有的锁定地点优先展示和剩余名额评分逻辑保留。

### 2. 拆分城市漫步路线规划

文件：`backend/app/agents/citywalk_agent.py`、`backend/app/services/citywalk_route.py`

- 把逐站选点、顺序与末站约束、距离和时间累计从 Agent 的 `execute()` 提取到 `CityWalkRoutePlanner`。
- `CityWalkAgent.execute()` 现在负责偏好解析、准备候选、委派路线规划和组装结果，结构与另外两个 Agent 一致。
- 地点构造改为使用共享方法；清理未使用的旧响应类型导入和 CityWalk 内未使用的讲述者属性。主 Agent 的讲述者流程不变。
- 简化已保证存在起点时的重复分支；保留对每段步行路线的实际检查。

**仍保留的功能差异：**漫步需要逐站考虑步行路线、已选地点和先后顺序，因此仍用逐站选择；景点和美食是同一地点周边的独立备选，仍使用批量评分。这些选择算法没有强行合并。

### 3. 统一请求中的公共字段

文件：`backend/app/models/travel.py`

- 新增 `TripPlanFields`，三个功能的请求共用行程 ID、版本、城市、起点名称、补充要求和锁定地点字段。各入口保留自己的参数、验证规则和现有额外字段处理方式。
- CityWalk 请求新增可选 `radius_meters`，与景点搜索半径共用同一个状态字段，范围为 500–10000 米。
- 原来 CityWalk 写死搜索半径 4000 米；现在默认使用状态的 5000 米，也可由请求指定。这会改变默认候选范围。
- CityWalk 的候选搜索现在使用共享的 `search_limit`，单类别候选上限相应从原来的目标站数调整为该搜索数量，并向搜索提供补充要求。这可能改变实际候选集合。

### 4. 修正数量边界不一致

文件：`backend/app/models/travel.py`、`backend/app/services/trip_service.py`

- 景点请求允许最多 100 个地点，原行程状态却只允许 10 个；状态上限与请求统一为 100。
- 搜索数量依旧按目标数量的两倍计算，但最多为 1000，避免大数量餐厅请求写出不能再次校验的行程状态。

### 5. 其他配套

- `backend/app/services/preferences.py`：明确自然语言中的 `radius_meters` 也可用于城市漫步。
- `backend/app/services/plan_changes.py`：城市漫步搜索半径变化可出现在版本变更说明中。
- `backend/tests/test_shared_discovery_pipeline.py`：验证三个功能共用搜索数量、各自半径、统一地点结果，以及数量状态可序列化恢复。

## 兼容性与已知限制

- 已保留锁定地点的历史版本、增量锁定、解锁及保存前校验。
- 旧的 `/walk/plan` 控制器仍调用当前不存在的 `plan_legacy`；这次没有删除该公共路由，也没有实现旧接口适配。相关旧测试原本已失败。
- CityWalk 的偏好解析仍需单独处理路线顺序和末站；没有删除旧 `WalkRequest` / 偏好模型，避免破坏现有调用和表单行为。
- 城市漫步只检查当前一段路线，由 Jev 选择下一站；锁定点的类别优先使用旧计划中保存的检索来源；对缺失来源的旧记录会尝试从历史版本恢复，仍无法恢复时不会凭空推断类别。
- 项目目录没有 Git 仓库元数据，无法提供自动 diff；上面列出本次修改的文件。

## 后续修复：锁定地点未进入类别候选

- 原问题：锁定地点虽然进入总候选池，但本轮搜索未命中它时，类别匹配为空，因此在按照当前类别过滤后会被排除。
- `PlannedPlace.matched_preferences` 保存选中地点实际命中的检索类别；旧计划可从原有的“检索偏好”原因恢复，也可从所选版本之前的历史恢复。
- 在城市漫步准备候选时，按真实历史检索类别恢复锁定地点的匹配关系；到了对应类别后将这些锁定地点与其他合适地点一起纳入候选，交给 Jev 判断当前先选哪个。同一类别需要访问多次时，按明确的类别顺序逐次选择不同地点。
- 搜索未返回其他地点时仍允许从锁定地点继续规划；不能满足距离、时间或顺序限制时仍会提示，未记录且无法恢复的类别不会猜测。
- 新增 `backend/tests/test_citywalk_locked_category.py`，覆盖搜索不再命中、自然语言锁定、全锁定、旧历史恢复、多地点同类别及无搜索结果。相关回归 95 项通过。
- 全量回归共 202 项，仍为 1 项失败、14 项错误，与上次的旧接口和候选搜索异常一致；没有调用真实第三方服务。

## 后续修正：同一类别访问多次时的锁定选择

- `CityWalkAgent.choose()` 在每个候选上标注 `is_locked`，并把尚未访问的锁定地点及已选地点的锁定状态传给 Jev；提示 Jev 决定本次先选择哪个地点，同时每个锁定地点在最终路线中只出现一次。
- 不再简单优先选锁定地点：同一类别需要访问两次时，锁定地点和其他地点均可成为本次候选，Jev 可以选择先去其他地点或先去锁定地点。
- Jev 根据剩余类别和站数考虑锁定要求；路线代码不会提前预留站位，已选地点从候选池移除。无法满足约束或 Jev 拒绝选择时不会保存缺失锁定地点的结果。
- 回归测试覆盖同类别两次访问的两种选择顺序、锁定地点只出现一次、无法重复选取已选地点，以及 Jev 拒绝选择时不保存。
- 相关回归 99 项通过；全量 206 项仍为此前的 1 项失败、14 项错误。使用离线替身，没有调用真实 Jev。

## 当前修正：显式合入类别候选，移除额外预筛选

- 删除 `enough_slots`、`can_reach_locks`、排列枚举及相应的 `if locked_by_id: feasible = ...`。
- 删除“剩余站位只允许选锁定点”的筛选和自动重复类别逻辑。
- 在当前 keyword 的普通候选产生后，显式合入对应的未访问锁定地点，以 POI ID 去重；不会因此删除其他候选。
- `choose()` 继续通过 `is_locked` 和 `required_locked_places` 告知 Jev 用户的保留要求，由 Jev 选择当前地点。
- 只检查当前候选路线的可用性、时长和距离；完成后核对锁定点是否均已选入，遗漏则不保存，不自动改写 Jev 的选择。
- 本次针对性回归 100 项通过，包括普通 shortlist 截断锁定点后显式补回、同类别两次访问的两种顺序、不预查未来路线、遗漏锁定地点不保存。本轮未重新运行全量测试；此前全量仍有旧接口和候选搜索相关失败。
