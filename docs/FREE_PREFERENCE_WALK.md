# 自由偏好与逐站规划

城市漫步不再选择五个固定主题。用户可自由组合公园、咖啡馆、书店或具体地点，并分别表达重要程度、游览顺序和最后一站。

## 数据怎么表达

```json
{
  "city": "上海",
  "start_location": {"longitude": 121.47, "latitude": 31.23},
  "interests": ["公园", "咖啡馆", "书店"],
  "visit_order": ["公园", "书店"],
  "end_with": "咖啡馆",
  "target_stops": 3,
  "available_hours": 3,
  "additional_requirements": "希望安静一点，尽量少走路"
}
```

- `interests` 按重要程度排列：以公园为主，咖啡馆和书店作为其他偏好。这个列表不决定实际先后。
- `visit_order` 表达明确的逐站先后：先公园，再书店。未列出的剩余站由模型根据偏好和位置选择。
- `end_with` 单独表达最后一站；若它与顺序列表最后一项相同，只占一个末站位置。
- `theme` 保留为可选名称和旧记录兼容字段，默认“自由漫步”，不再对应固定搜索词模板。
- 总地点数仍由 `target_stops` 控制。增加一种偏好，不等于增加总数量。

顺序和末站需要的站数超过目标数时返回错误，不悄悄扩大总数。同一类别可在顺序里重复，但同一 POI 不重复访问。

## 表单和对话如何更新偏好

表单传入结构化兴趣、顺序和末站。`WalkPreferencePlanner` 结合补充要求生成有界的 `WalkSearchProfile`：中文检索词、英文决策说明、明确顺序与末站。模型不会生成 POI 和坐标；显式提交的偏好不能遗漏，顺序不能擅自改变。

对话入口先抽取 `PreferencePatch`，再由城市漫步的请求转换处理编辑操作：

| 用户要求 | 处理 |
|---|---|
| “加一家咖啡店” | 默认 MERGE，保留公园等旧偏好，新增咖啡店；不自行改变总数 |
| “公园不去了” | removed_interests 移除对应旧词，并清理无效的顺序和末站 |
| “以书店为主” | priority_interests 调整主次，保留其他偏好 |
| “全部改成只逛书店” | interests_mode=REPLACE，替换正向偏好并移除不再适用的顺序要求 |
| “咖啡馆放最后” | end_with 更新，其他偏好继承 |
| “先书店再公园” | visit_order 更新；与重要程度分开 |
| “总共五个地点” | 更新目标总数，仍经过数量范围校验 |

`rename_theme` 只在明确命名或重命名时使用；增加咖啡店不会自动重命名公园行程。路由提示也明确区分“路线里增加餐饮一站”和“切换成独立餐厅推荐”。

旧快照没有新增字段时，默认顺序为空、末站为空。没有兴趣、只有旧主题文字的行程，在添加偏好时保留旧文字作为迁移上下文，不再查固定主题映射表。

## 每一站怎么选

```text
自由偏好与补充要求 → 结构化检索计划
    ↓
ReAct按每个偏好搜索起点周边4km → 读取高德字段审核 → 有不合格地点则改词重搜一次
    ↓
只保留审核通过的POI → 按ID去重并记录原偏好的检索来源
    ↓
每轮：当前位置 + 未完成顺序 + 末站要求 + 剩余时间和距离
    ↓
挑出本轮候选 → 并发查询真实步行路线 → 代码过滤预算
    ↓
Jev从可行POI ID中选择下一站，或明确拒绝
    ↓
记录路线和停留 → 更新当前位置与预算 → 下一轮
```

每个偏好保留最多 `max(3, target_stops)` 个近处候选，避免一类地点占满候选池。每轮最多核实12个候选，保留请求内高德四并发限制。初始检索完成后不反复扩大半径，当前不是实时 GPS 导航。

Jev 输入包含：按重要程度排列的英文偏好、尚未覆盖的偏好、明确顺序、末站、当前位置经纬度、已选地点、剩余站数、剩余分钟，以及候选的真实步行距离和时间。候选 ID 必须属于本轮已核实集合。

只有明确顺序或末站时，代码才按当前阶段收窄候选。普通兴趣不会为了覆盖固定主题而强制轮换类别。选中的顺序直接作为最终路线，不再用近邻法重新排序。

检索来源表示“为哪个原始偏好搜到”。候选先经生成模型的 ReAct 工具循环审核，排除酒店管理公司等不符合类别的结果，再交给 Jev 选点。审核基于高德记录中的名称、类别和地址，不代表核验“正宗”、菜单或开放时间等额外事实。流程见 [ReAct候选检索](REACT_CANDIDATE_SEARCH.md)。

## 预算、失败和修改说明

偏好解析先得到 `WalkSearchDraft` 草稿，再由代码应用表单或对话中明确的 `visit_order`、`end_with` 和清除操作，最后校验检索词引用。明确字段由代码保留，只有未指定的顺序和末站才从补充要求中推断。末站统一在路线阶段计数：若它已是顺序最后一项，仅计一次；更早出现的同类地点仍保留，偏好解析阶段不再次删除末项。例如“书店、博物馆、公园”加末站“陕西菜馆”，不会因模型把餐馆追加到顺序列表而误报偏好解析失败，仍需四个目标地点。缺失检索词或引用未知类别仍会被拒绝。

停留估计为 `max(25, min(55, round(hours*60/target)-15))` 分钟。每轮检查累计步行、停留估计与可用时长，并检查可选的总步行上限。不包含排队、预约等待与返程，不能保证实际出游精确用时。

顺序或末站没有合适候选时停止追加并说明未满足项，不用其他类别冒充。可形成至少两站时返回缩短方案，否则返回错误。路线整体不可用时作为外部服务错误处理。

状态保存解析后的兴趣主次、顺序与末站，历史恢复和表单编辑可继续使用。`plan_changes` 比较它们并交给对应讲述者说明真实修改。`TripState._walk_edits` 仅记录本轮明确清除的顺序、末站和移除的偏好，防止旧备注使其复活；它是私有属性，不进入数据库 JSON 或 API 响应。
